## Delivered

- Two modes ([decision 0016](../../decisions/0016-template-lifecycle.md#two-modes)):
  the template's own repository keeps `repository.mode = "maintainer"` and
  the core's acceptance suite; an exported project has neither. Bootstrap
  now sets up only the components a check would activate, so a helper bundle
  whose profile no application uses is reported as
  `quality-<language>-helper: dormant, so its <language> tools wait` and its
  toolchain is never downloaded, until the candidate changes the helper.
- `[template]` in the policy: `exclude` (the plan records, `PLAN.md`, and
  the acceptance harness) and `fenced` (six files with maintainer-only
  regions: `quality.toml`, the core's `scenarios.toml`, `README.md`,
  `AGENTS.md`, the documentation index, and the core README).
- `quality template export DIRECTORY [--rev REV]` (`quality/template`,
  `cli/template_cmd.py`):
  - exports the tree of a commit, never the working tree, into a new or
    empty directory, leaving out the excluded paths and the fenced regions;
  - stops with `template.invalid` (exit 2) on a broken or nested fence, a
    fenced file that is missing, not exported, or not UTF-8, a submodule, a
    link to a left-out path, or a source or exported policy that does not
    validate;
  - writes into a staging directory beside the target, makes it a
    repository on the policy's `default_branch`, and commits every exported
    file as the root commit `Start from the quality template` with a
    `Quality-Template: <commit>` trailer. The commit carries the user's
    identity from the Git variables or their configuration, with
    `user.useConfigOnly` so Git cannot guess one; without an identity the
    export fails with exit 3 and leaves nothing (`gitio.create_repository`).
    The staging directory becomes the target last;
  - the launcher prepares uv, CPython, and the core for `template export` as
    for `bootstrap`, because a fresh clone has nothing installed.
- `quality component add ROOT [--id] [--profile] [--source] [--unit]
  [--capability | --no-boundary-reason]` (`cli/component_cmd.py`,
  `policy/edit.py`): detects the profile from the root's manifest, takes the
  profile's conventional directories, appends one `[[components]]` table
  after the last component without rewriting comments or order, and writes
  only a policy that validates; an inline component array is refused.
- `quality tools update NAME VERSION` (`toolchain/update.py`,
  `cli/tools_cmd.py`): every tool of `toolchains.toml` names its vendor's
  checksum file in `checksums`; the update replaces the version in the URLs
  and members, takes the checksums from that file, hashes the extra files,
  rewrites only that tool's lines, and checks that the result parses to the
  old manifest with only that tool changed (`tools.update-invalid`, exit 2;
  `tools.update-failed`, exit 3). The gitleaks rule set is now fetched at
  the release tag, whose content is the pinned commit's.
- Adapter contract tests (`tests/unit/test_profile_contract.py`) run the same
  checks for every `Profile` member: each stage knows the profile, its rules
  are registered and explained, it expects coverage of its own sources only,
  an empty or malformed report never passes, and source of another or an
  unsupported language fails classification.
- uv installs CPython with `--no-bin` in the launcher and in Python
  provisioning. Before, `uv python install` also linked `python3.14` into
  the user's `~/.local/bin`; the lifecycle acceptance test found it, because
  the scratch user's home received the link.
- Tests of the lifecycle:
  - the core's end-to-end suite exports a project from a fresh clone and
    checks what was left out, rewritten, and committed (scenario
    `template-export`);
  - `tests/acceptance/test_template.py` (scenario `template-lifecycle`, not
    exported) has four independent tests, each exporting its own project
    from a clone of the candidate: two bootstraps with a cache that holds
    only uv, CPython, gitleaks, actionlint, and osv-scanner; the first
    commit with a Python component through the hook, with the same cache;
    a change to a dormant helper; and two Python, a TypeScript, a Dart, and
    a PHP component added in one commit through the hook.
- Faster suites: the core runs its unit, end-to-end, and acceptance suites
  on one pytest-xdist 3.8.0 worker per CPU (`-n auto` in its pytest
  settings; [decision 0009](../../decisions/0009-python-profile.md#suites)).
  pytest-cov combines the workers' coverage, which a new runner test proves
  for a component that locks pytest-xdist. No test depends on another or
  carries an `xdist_group` mark, which would rename it in the JUnit report
  that scenarios are matched against. The acceptance suite sorts the
  lifecycle tests first. The process tests that kill a process group wait
  up to 60 seconds for it to go, because a loaded machine is slow to reap.
- Documentation: the template `README.md` and `AGENTS.md`, the documentation
  index, the [profile support matrix](../../reference/profiles.md), the
  [architecture](../../guides/architecture.md),
  [exceptions](../../guides/exceptions.md),
  [extension](../../guides/extending.md), and
  [maintenance](../../guides/maintenance.md) guides, decision 0016,
  decisions 0001, 0002, 0003, and 0010 amended, the
  [command-line reference](../../reference/cli.md), and the core README.

The first parallel acceptance run found two problems. Grouping tests with
`xdist_group` appended `@<group>` to their JUnit names, so the gate reported
the end-to-end scenarios as `scenarios.absent`; the marks were removed and
`test_template.py` was split into tests that each export their own project.
In a nested gate under a load average of about 25, the process test
`test_reap_kills_what_outlives_a_normal_exit` timed out waiting five seconds
for a killed process to go; it did not fail with 24 workers alone, and now
waits up to 60 seconds for children that would sleep for ten minutes.

## Limitations and follow-ups

- Every change to `quality.toml` or `tools/quality` reruns the core's suites
  in each affected project, so the lifecycle tests run nested gates of
  several minutes each; A16 alone bounds the acceptance suite at about nine
  minutes on any number of workers. The suite timeout is two hours for
  machines with few CPUs.
- Each revision or merge check runs gitleaks twice, over the tree and over
  the history, about a second each; merging the two scans is a possible
  follow-up.
- Docker on this machine refuses unprivileged user namespaces, so the
  container run checked the unit suites with the network (`tests.network`);
  the hosted runner of P10 had them.
- The exported decision records mention the acceptance harness that the
  export leaves out.
- pytest-xdist is a pytest plugin of the core's development group, not a new
  test framework (R01.6); a project may lock it or not.
- Earlier phases ran `uv python install` without `--no-bin`, which left a
  `python3.14` link in this machine's `~/.local/bin`; it belongs to the
  user's environment and was left in place.
