## Delivered

- Behavioral scenarios ([decision 0014](../../decisions/0014-behavioral-scenarios.md)):
  - capabilities: every component declares `capabilities` or a
    `no_boundary_reason`, never both or neither. The catalog
    (`scenarios/catalog.py`) gives each of library, cli, http-api, database,
    migrations, contracts, queues, ui, and authorization its mandatory and
    optional requirements and the suites that may prove them;
  - manifests: a versioned TOML file per component (schema
    `docs/reference/scenarios.schema.json`, generated with the policy
    schema) whose scenarios have an ID, a capability, a level, a stage,
    requirements, OpenAPI operations, and test selectors; `[[not_applicable]]`
    excuses optional requirements with a reason, and `[[retired]]` records
    removed scenarios;
  - static rules on every `check` and in `quality scenarios`:
    `scenarios.manifest`, `reference`, `uncovered`, `level`, `ambiguous`,
    and `deleted` (a scenario of the base revision that is neither kept nor
    retired), plus OpenAPI reconciliation in both directions;
  - proof: after the suites run, each required scenario's selectors are
    matched with the fresh results of this run. A failure, a skip, an
    expected failure, a missing or renamed case, an ambiguous exact name, or
    a suite without results fails (`scenarios.failed`, `skipped`, `absent`,
    `ambiguous`, `unverified`), with similar case names as hints;
  - stages: `commit` (the hook and the default) and `merge`
    (`check --stage merge`, which also requires the commit scenarios); a
    stage runs the unit suite and the levels of its required scenarios, and
    `quality test` proves the scenarios of the suites it ran. Text and JSON
    reports carry one summary per component;
  - quarantine: `[[quarantine]]` entries in `quality.toml` for non-unit
    suites with a reason, an owner, an expiry, and the scenarios they
    suspend. The test still runs and is reported (`tests.quarantined`), its
    failure does not fail its suite, it proves nothing, and a scenario that
    maps it without being named fails (`scenarios.quarantined`); expired
    and unused entries fail (`quarantine.expired`, `quarantine.unused`);
  - suggestions (`scenarios.suggestion`, info) from well-known dependencies,
    executables, an OpenAPI document, and a migrations directory;
  - enhanced profiles: `property` and `performance` need a tagged scenario,
    performance outside the unit suite; `mutation` is refused with
    `scenarios.enhanced` because no profile runs a tested mutation tool.
- Runners: pytest runs with `xfail_strict=true` and without the
  `rerunfailures` and `flaky` plugins, and an `xfail` is an expected
  failure; Vitest runs with retries off and a gate reporter that marks
  `test.fails` cases as expected failures, passes after a test's own retry
  as failures, and counts errors outside tests; `dart test` runs with
  `--no-retry` and a `solo` run is `tests.focused`; PHPUnit's exit status 2
  is a test failure status.
- Commands: `quality scenarios [--rev REV] [--json]`, `check --stage`,
  `policy schema --scenarios`, and `self-test --level e2e`.
- This repository: the core and the launcher declare `cli` with manifests
  and new e2e suites that run the exported template, copied without
  installed environments, through `./quality`; the core proves its commit
  gate with acceptance tests at the merge stage. The three helpers state
  why they have no boundary.
- Reference fixtures in `quality.testkit`: `greet`, a library with a command
  line whose e2e suite builds and runs a zipapp, and `notes`, an HTTP API on
  the standard library with SQLite, numbered migrations, an OpenAPI
  document, and writer-only creation. Both pass the gate.
- Documentation: decision 0014, the [test quality guide](../../guides/test-quality.md),
  decisions 0007, 0008, 0009, 0011, 0012, and 0013 amended, the
  [command-line reference](../../reference/cli.md), the
  [documentation index](../../README.md), the core README, and `AGENTS.md`.

## Limitations and follow-ups

- Scenario selectors are case names as each runner reports them; renaming a
  test is a manifest change. PHPUnit names separate namespaces with dots.
- Suggestions are heuristics over manifests and files; they are never
  required, and a capability nobody declares is not enforced.
- Contract requirements are optional, because a mock of a third party
  proves no compatibility; only owned consumers and providers can be
  verified.
- Mutation testing is refused rather than enforced until a profile runs a
  tested mutation tool. Property and performance profiles check that a
  tagged scenario exists and passes, not the quality of its generator or
  its timing budget.
- Retries are closed per profile as listed above; a runner plugin the gate
  does not know about could still rerun tests inside one case.
- The merge stage is selected with `check --stage merge`; wiring it into CI
  is P10.
