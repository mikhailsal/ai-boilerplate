# 0006 Discovery and classification

Status: accepted (P02); amended in P05.

Every candidate file gets a category, an owning component, and a language.
Discovery reads the materialized snapshot only (decision 0004) and never runs
repository code.

## Components are declared, manifests are checked

Components are declared in `quality.toml`. Manifests validate those
declarations but never create components, so adding a `package.json` cannot
silently change which gates apply.

- The owner of a path is the component with the longest root containing it;
  the root `.` is the least specific.
- Inside its owner a path is in a test root, a source root, or elsewhere, in
  that order of precedence.
- `pyproject.toml`, `setup.cfg`, `setup.py`, `package.json`, `pubspec.yaml`,
  and `composer.json` are parsed as data; `setup.py` is never executed. It
  declares a package only when it imports `setuptools` or `distutils`, so an
  ordinary module that happens to be named `setup.py` is not a manifest.
- A package manifest at a component root must match the component profile
  (`discovery.profile-mismatch`).
- A package manifest anywhere else fails (`discovery.manifest-outside-component`)
  unless it also declares a workspace (uv workspace, npm `workspaces`, Dart
  pub `workspace`). Tool-only files such as a `pyproject.toml` without
  `[project]` may sit anywhere.
- Manifests in test roots and explicitly classified manifests are fixtures and
  are not interpreted. Unparseable or symlinked manifests fail
  (`discovery.manifest-invalid`).
- Every declared component, source, and test root must contain a tracked
  file (`discovery.missing-root`), so a typo cannot leave a gate with nothing
  to check.

## File types

Detection uses names and extensions first, then the `#!` line of files
without an extension. The order is: special names (dotfiles, `Dockerfile`,
`requirements*.txt`, code-like configuration such as `setup.py`,
`conftest.py`, `*.config.ts`, `rector.php`), code extensions, documentation
extensions and stems (`LICENSE`, `CHANGELOG`), configuration extensions, and
asset extensions. Shebangs follow `env` and its options and drop version
suffixes (`python3.14` is Python). Anything else is unknown.

Code in languages without a profile (shell, Go, Rust, C, and others) is
detected so that it cannot pass unchecked.

## Categories

| Situation | Category | Finding |
| --- | --- | --- |
| Any file in a test root | `tests` | none; fixtures may have any type |
| Profile code in a source root, including code-like configuration names such as `setup.py` or `conftest.py` | `source` | none |
| Code in a language without a profile | `source` | `discovery.unsupported-language` |
| Code outside every component | `source` | `discovery.unowned-source` |
| Code outside the source and test roots of its owner | `source` | `discovery.unowned-source` |
| Code or code-like configuration of another profile | as detected | `discovery.language-mismatch` |
| Documentation, configuration, assets | `docs`, `config`, `assets` | none |
| Unknown type outside test roots | `assets` | `discovery.unclassified` |

## Explicit classification

`[[classification]]` entries carry a pattern, a category, and a reason.
Patterns must start with a literal name and match the full path.

- `source` and `tests` cannot be assigned (`policy.conflict`); membership in
  those categories comes from declared roots only.
- Inside source roots, an entry applies only to files with a generator marker
  in their first 1 KiB (`@generated`, `Code generated`, `DO NOT EDIT`,
  `auto-generated`, `generated by`) and only as `generated`. Anything else is
  `discovery.classification-relabel` and the file stays `source`, so a
  classification cannot exempt code from its gates.
- In test roots and outside roots, an entry may assign `docs`, `config`,
  `generated`, `vendor`, or `assets`. A classified file skips the language
  checks; this is how vendored code in another language is admitted.
- A file matched by two entries fails (`discovery.classification-conflict`)
  and keeps its natural category.
- An entry that matches no file warns (`discovery.unused-classification`), so
  stale exemptions stay visible.

## Submodules and symlinks

Gitlinks are opaque. They pass only when classified as `vendor`; otherwise
they fail with `discovery.submodule-unsupported`. The snapshot holds an empty
directory in their place. Symlinks are classified by name and never followed
for type detection; decision 0004 keeps their targets inside the snapshot.

## Helper activation

Application and tooling components always run. A helper component runs when:

- the repository is in maintainer mode;
- an application component uses the helper's profile; or
- the candidate changes a file under the helper root.

A Python-only project therefore does not need Node, Dart, or PHP toolchains
for dormant helpers, but editing helper code wakes the helper's gates.

## Output of unusual paths

Text output escapes C0 and C1 control characters, DEL, and undecodable bytes
(`\x1b`, `\x0a`, `\xff`), so a file name cannot drive the terminal or forge
extra lines. JSON output is ASCII-only; undecodable bytes appear as the
surrogate escapes `\udc80`–`\udcff` that Python's `os.fsdecode` produces.

## Inspecting discovery

`quality inventory [--rev REV] [--json]` materializes the candidate and lists
each file's category, component, and language with the discovery findings.
Without `--rev` it uses the caller's `GIT_INDEX_FILE`, resolved against the
current directory, so hooks that run with a temporary index see the same
candidate.

## Git version

The core requires Git 2.34 or newer (Ubuntu 22.04). It does not use
`ls-tree --format` or `merge-tree --write-tree`, and it does not assume that
the empty blob exists in the object database.
